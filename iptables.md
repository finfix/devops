# iptables — аудит портов coin-1

Снимок реального `ss -tulnp` с сервера `coin-1`. Колонка "Куда фильтровать" — целевое состояние (что должно быть в правилах `FRONTDOOR`), не текущее.

Общая методика построения такой таблицы и сам firewall-скелет — в личной базе знаний (заметка `iptables` в Obsidian, раздел "Best practice: однонодовый сервер с k3s").

## Таблица портов

| Порт | Протокол | Процесс | Кому реально нужен | Куда фильтровать | Комментарий |
|---|---|---|---|---|---|
| 80 | tcp | nginx (ingress) | весь мир | публично | HTTP, обычно редирект на 443 |
| 443 | tcp | nginx (ingress) | весь мир | публично | основной вход, TLS |
| 8181 | tcp | nginx | ? — уточнить, что за vhost | публично, если реальный сервис; иначе закрыть | второй nginx-вход без явного TLS на этом порту, не описан в общей схеме — нужно понять назначение |
| 2002 | tcp | sshd | ты | только через WG (`-i wg0`) | сейчас, судя по всему, слушает на `0.0.0.0` — открыт всему интернету |
| 6443 | tcp | k3s-server (kube-apiserver) | ты (kubectl), CI/CD | только через WG (`-i wg0`) | слушает на `*` (все интерфейсы) — критично, apiserver виден снаружи |
| 10250 | tcp | k3s-server (kubelet) | control-plane, сам себе | только `lo`/internal, никогда WAN | слушает на `*` — при включённом anonymous-auth это открытый RCE-вектор в кластер |
| 10254 | tcp | nginx-ingress-controller | Prometheus/health-check внутри кластера | только internal (`lo`/pod-сеть), не WAN | стандартный `/healthz` и метрики ingress-controller'а, не предназначен для публики |
| 8443 | tcp | nginx-ingress-controller | зависит от роли (обычно admission webhook или второй listener) | internal, не WAN, если это не отдельный публичный сервис | нужно свериться с конфигом `k8s/config/ingress-nginx`, что именно на нём висит |
| 9100 | tcp | node_exporter | Prometheus (внутри кластера/через WG) | только `lo`/internal или через WG | публично отдаёт метрики хоста (CPU, память, диски, интерфейсы) — разведка для атакующего, не RCE, но точно не для WAN |
| 8472 | udp | flannel VXLAN | другие ноды кластера | internal only, в single-node не нужен наружу вообще | слушает на `0.0.0.0`, но при single-node трафика туда быть не должно |
| 51820 | udp | WireGuard | твои доверенные peers | публично | единственный порт, которому положено быть открытым помимо 80/443 |

## Что сделать по итогам

**Критично (реально открыто всему интернету прямо сейчас):**
- `6443/tcp` (kube-apiserver) — ограничить `-i wg0`
- `10250/tcp` (kubelet) — убрать с публичного интерфейса полностью; kubelet не нужен снаружи хоста даже через WG в single-node конфигурации
- `2002/tcp` (SSH) — перевести на `-i wg0`, снять с `eth0`
- `9100/tcp` (node_exporter) — закрыть от WAN, оставить только через WG или `lo`, если Prometheus и node_exporter на одном хосте

**Требует уточнения (что это и должно ли быть публичным):**
- `8181/tcp` — какой vhost там висит и нужен ли он извне
- `8443/tcp` — какая роль у этого listener'а ingress-controller'а (webhook/second entrypoint), не публичный по умолчанию смысл

**Не трогать:**
- `80`/`443` — целевое поведение, публичный вход
- `51820/udp` — целевое поведение, единственная легитимная публичная "дверь" помимо веб-порта
- `8472/udp` — не публичный по смыслу, но при single-node не является активной угрозой (нет других нод, которые могли бы туда стучаться легитимно) — закрыть заодно с остальным при накате `FRONTDOOR`

## Ссылка на прошлый скан (nmap снаружи)

Ранний внешний скан этого же хоста уже показал `6443/tcp open`, `10250/tcp open` — этот `ss`-снимок подтверждает то же самое с локальной стороны (сокеты реально слушают на `0.0.0.0`/`*`, а не только на `127.0.0.1`), то есть расхождения между "что слушает" и "что должно быть видно" нет — оба источника согласны, что это дырки.

iptables -N FRONTDOOR
iptables -A FRONTDOOR -i lo -j ACCEPT
iptables -A FRONTDOOR -m state --state ESTABLISHED,RELATED -j ACCEPT
iptables -A FRONTDOOR -p tcp --dport 2002 -j ACCEPT
iptables -A FRONTDOOR -p tcp --dport 80  -j ACCEPT
iptables -A FRONTDOOR -p tcp --dport 443 -j ACCEPT

iptables -I INPUT 1 -j FRONTDOOR
